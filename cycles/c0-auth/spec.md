# C0 · 账号与权限体系 · 需求规格

> 版本 v0.1 · 2026-11-07
> 状态：**待评审**（通过后才进入设计）
> 版本号：v0.1.0

---

## 一、一句话目标

让「**谁能登录、登录后能看到什么**」这套规则真正可用：

> 老师用自己的微信登录，只看到自己名下的学员；
> 老板登录看到全部，并能不停服务器就给新老师开号、给离职老师停号。

**否证条件**：如果老师账号能看到别人的学员，或开一个新号必须改代码/重启服务，本周期失败。

---

## 二、为什么是这件事

| 事实 | 后果 |
| --- | --- |
| 现在 `SecurityConfig` 只放行 `/api/health`，其余一律 401 | **任何业务接口都调不了**，C1 无从开始 |
| C1 的核心规则是「老师只看已核实且归属自己的学员」 | 没有身份与角色，这条规则无处落地 |
| 已发生过三次员工离职（曼曼 / 艺帆 / 璇子） | 账号必须能停用，**且历史记录不能跟着消失** |
| 三张表（`app_user` / `app_role` / `app_user_role`）已在 V001 建好 | 本周期只补**运行逻辑**，不重建结构 |

---

## 三、用户与角色

| 角色 | 人 | 能做什么 | 数据范围 |
| --- | --- | --- | --- |
| `owner` | 老板 | 全部功能 + 账号管理 | ALL（全部数据） |
| `teacher` | 柒柒、三水 | 业务功能 | SELF（只看自己名下） |
| `operator` | —（预留） | C0 不实现具体权限 | — |

**一个人可以有多角色**（`app_user_role` 是多对多），本周期不阻止，但默认每人一个。

## 四、核心流程

### 4.1 登录

```
小程序 wx.login
   → code
   → POST /api/auth/login {code}
   → 后端调微信 code2Session（用 appid + secret）
   → 拿到 openid
   → 查 app_user（openid + status=ACTIVE）
        ├─ 没有或已停用 → 403（无权限）
        └─ 有 → 查角色 → 签 JWT（7 天）
   → 返回 {token, user:{id,name,roles}}
```

**没有密码、没有注册。** openid 是唯一凭证；账号只能由老板开通。

### 4.2 鉴权

```
请求带 Authorization: Bearer <token>
   → 解析 JWT → 取 userId
   → 查库确认 status=ACTIVE（★ 不信任 token 里的状态）
   → 把 user + roles 注入 SecurityContext
   → 按路径与角色判断
```

**每次请求都查一次库**：3 个用户，一次主键查询的成本可以忽略；换来的是**停用账号立即生效**，而不是等 token 过期。

### 4.3 数据范围

| 角色 | 规则 |
| --- | --- |
| `owner` | 不加过滤 |
| `teacher` | 按 `app_user.staff_id` 对应到 `app_staff.id`，只看归属自己的记录 |

**实现约定**：数据范围判断只写在一个地方（`DataScopeService`），业务代码调用它，不各自拼 SQL。

### 4.4 账号开通与停用

```
开通：POST /api/admin/users {staffId, name, openid, roleCode}
停用：PATCH /api/admin/users/{id} {status: DISABLED}
改角色：PATCH /api/admin/users/{id} {roleCodes: [...]}
```

**停用不影响历史**：`app_user.status=DISABLED`，`app_staff` 记录保留，历史跟进记录仍指向该 staff。

## 五、规则

| # | 规则 |
| --- | --- |
| 1 | `openid` 唯一；一个 openid 只能对应一个 `app_user` |
| 2 | JWT 有效期 7 天；过期后小程序静默重新 `wx.login` |
| 3 | 未登录 → **401**；已登录但角色不够 → **403**；越权访问他人数据 → **404** |
| 4 | 账号停用后，已发出的 token **立即失效**（靠每次查库） |
| 5 | 所有响应沿用统一格式 `{code,msg,data}` |
| 6 | 日志里不出现 openid 全串（脱敏为前 4 后 4） |

## 六、接口清单（5 个）

| 接口 | 谁用 | 作用 |
| --- | --- | --- |
| `POST /api/auth/login` | 所有人 | code → token |
| `GET /api/auth/me` | 所有人 | 当前用户 + 角色（小程序启动时校验登录态） |
| `GET /api/admin/users` | owner | 账号列表 |
| `POST /api/admin/users` | owner | 开通账号 |
| `PATCH /api/admin/users/{id}` | owner | 停用 / 启用 / 改角色 |

**不做** `logout` 接口——token 在客户端，删掉即可。

## 七、小程序侧

| 页面 | 内容 |
| --- | --- |
| 启动逻辑 | 有 token 先 `/auth/me` 校验；无或失效 → 静默 `wx.login` 换 token |
| 无权限页 | 显示「你的微信号还没有开通，请联系老板」+ 微信号脱敏后四位 |
| 我的页（改造） | 显示姓名、角色、退出登录 |

## 八、非目标（C0 一件都不做）

- ❌ 密码登录 / 找回密码 / 自助注册
- ❌ 细粒度权限点（按钮级、菜单级）
- ❌ 组织架构、部门、多门店
- ❌ 操作审计日志（等 C1 有真实操作了再加）
- ❌ 小程序管理界面（**用命令行脚本管理账号**，见下）
- ❌ SSO / 企业微信登录

> **关于管理界面**：3～10 个账号，做页面是浪费。C0 提供接口 + 一个 `ops/admin.ps1` 命令行工具
> （`list` / `create` / `disable` / `role`）。等账号真到几十个再考虑界面。

## 九、Definition of Done

| # | 验收 | 怎么证明 |
| --- | --- | --- |
| 1 | 未开通的微信登录 → 403 | 用一个不在库里的 openid 调登录 |
| 2 | 开通后同一 openid 登录成功 | 返回 token + 姓名 + 角色 |
| 3 | teacher 只看自己 | 用 teacher 的 token 访问 owner 接口 → 403 |
| 4 | 停用立即生效 | 停用后拿旧 token 请求 → **401**（不是继续放行） |
| 5 | 开号不用改代码/重启 | 通过 `/api/admin/users` 创建，随即能登录 |
| 6 | 未登录一律 401 统一 JSON | 任意接口不带 token |
| 7 | 冒烟脚本覆盖登录链路 | `ops/smoke.ps1` 新增用例，本地与线上都跑通 |

## 十、开放问题（需要你定）

| # | 问题 | 我的建议 |
| --- | --- | --- |
| 1 | **AppSecret**：`code2Session` 必需，现在没有 | 开发期先用 **mock 登录**（白名单 code → 固定 openid），真实登录等你把 secret 写进服务器 `app.env`。**这个必须先定，否则登录链路无法真验** |
| 2 | 管理账号用命令行还是小程序页面 | **命令行**（`ops/admin.ps1`），理由见第八节 |
| 3 | 老师离职后名下学员怎么转 | C0 只停账号；转归属属于 C1 的业务动作（核实台有「改派」） |
| 4 | 是否允许一人多角色 | 表结构支持，C0 不阻止，默认一人一角色 |

## 十一、依赖与风险

| 项 | 说明 |
| --- | --- |
| 依赖 AppSecret | 没有它，真实微信登录跑不通（可用 mock 先过） |
| 依赖小程序域名 | 真机/体验版才需要；开发者工具用 localhost 不受影响 |
| 风险：mock 与真实逻辑分叉 | mock 只替换「code → openid」这一步，其余代码路径完全一致 |
