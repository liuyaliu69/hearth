让柒柒、三水、老板三个人，在手机上完成这条链：

## 二、为什么加核实环节（失败归因）

上个月没执行下去，**不是老师嫌工具难用，是数据不准让老师不敢用。**

| 失败路径 | 解法 | 本规格对应 |
| --- | --- | --- |
| 老师打过去，剩余课时 / 到期日 / 归属人对不上 | 做更简单的界面 | ❌ 无效 |
| 老师发现信息错，第二次就不打了 | **先让数据可信，再谈跟进** | ✅ 人工核实闸门 |

**仓库里已有的数据质量证据**：退款不可见、160 单实收 ¥0 涉 7,357 课时、39 个会员叫「微信用户」、`member.member-expiring` 返回 0、21 种编外产品。

**核心判断**：产品的第一价值不是「方便」，是「可信」。

## 四、核实状态机

```
              ┌─ CONFIRM ──→ VERIFIED ──┐
PENDING ──────┼─ FIX ──────→ VERIFIED ──┼──→ 分发到老师 ──→ 老师记录结果
              ├─ REJECT ───→ REJECTED   │
              └─ PARK ─────→ PARKED ────┘
                                  │
       老师标「信息有误」──────────┴──→ 退回 PENDING（TEACHER_FLAGGED）
```

| 状态 | 含义 | 是否分发给老师 |
| --- | --- | --- |
| `PENDING` | 待核实（默认） | ❌ |
| `VERIFIED` | 已核实，数据可用 | ✅ |
| `REJECTED` | 已排除，这人不用跟 | ❌ |
| `PARKED` | 挂起，以后再说 | ❌ |

「后面再核实」对应 PARKED：不进分发、不算核完，工作台持续显示积压数。

## 五、疑点规则 v1（系统自动标，不自动放行）

| 代号 | 判定条件 | 为什么要标 |
| --- | --- | --- |
| `MOBILE_BAD` | 手机号不是 11 位纯数字 / 含星号 / 与其他记录重复 | 打不通，或打错人 |
| `SILENT_BALANCE` | 次卡剩余课时 > 0 且 距末课 ≥ 180 天 | 有钱没上课，状态最不确定 |
| `STATE_CONFLICT` | 时间卡剩余天数 < 0 且 次卡剩余课时 > 0 | 两个字段互相矛盾 |
| `TEACHER_LEFT` | 分配老师属于已离职名单（曼曼 / 艺帆 / 璇子，可配置） | 30/39 到期客户无人对接的直接原因 |
| `NO_SHOW_199` | 买过 199 = 1 且 到课次数 = 0 | 可能只是下单没来 |
| `NO_MOBILE` | 手机号为空 | 没法打 |
| `CARD_NO_CLASS` | **次卡剩余课时 > 0 且 到课次数 = 0** | 买了课包一次没来：要么漏课，要么录入有错，是最该核实的一类 |

> **为什么 `CARD_NO_CLASS` 不并进 `SILENT_BALANCE`**：
> `SILENT_BALANCE` 依赖「距末课天数 ≥ 180」，而**从未来过的会员根本没有这个字段**
> （真实导出里 `最后上课` 与 `距末课天数` 全为空）。
> 并进去的结果是：这类人永远不命中，而他们恰恰是剩余课时最多的一群。
>
> 真实案例（2026-11-10 核对导出文件）：曹春菊，次卡剩余 **375** 课时，到课 **0** 次，
> v1 六条规则全部不命中。

> 规则可配置：新增/停用不改代码。命中率长期 > 40% 说明太松，< 5% 说明太紧。

### 优先级：临期 > 疑点（已确认）

**疑点决定「这条要不要核」，临期决定「先核谁」。**

- 任何「时间卡剩余天数 0–30」的记录，**不论是否命中疑点**，都进置顶分组「临期待核」
- 各分组内部排序：临期者优先，其次按剩余天数升序
- 老师端同理：🔴 临期队列永远排第一

## 六、核实的四种动作

| 动作 | 做什么 | 结果 |
| --- | --- | --- |
| **确认** `CONFIRM` | 数据没问题 | → VERIFIED |
| **修正** `FIX` | 改字段后再确认（只允许改 4 个关键字段） | → VERIFIED，原值留痕 |
| **排除** `REJECT` | 这人不该跟 | → REJECTED |
| **挂起** `PARK` | 现在判断不了 | → PARKED |

**所有动作写 `followup_review_log`**：谁、何时、动了哪个字段、原值、新值。

| 分组（系统自动） | 整批动作 |
| --- | --- |
| 🔴 **临期且待核实**（跨疑点，置顶） | 整批确认跟进 |

| 无疑点 | 一键全部通过 |

## 八、核实结果继承（★ 最容易做错、也最劝退的一环）

> 新快照导入时，若该学员上次状态为 `VERIFIED`，且**关键字段没有变化** → **继承 VERIFIED，不打扰你**。
> 关键字段任一变化 → 退回 `PENDING`，标 `CHANGED`，进入复核队列。

**关键字段只有 4 个**：手机号 / 次卡剩余课时 / 时间卡到期日 / 归属老师。

**保护条款**：已分发给老师的人，即使因数据变化退回 `PENDING`，**老师端仍然可见**，只标「数据待确认」。

## 十、数据质量指标（C1 就要开始记）

| 指标 | 含义 | 期望 |
| --- | --- | --- |
| 疑点命中率 | 命中疑点人数 / 总人数 | 10–30%。>40% 规则太松 |

| 老师退回率 | 「信息有误」次数 / 已分发人数 | 应逐周下降 |
| 待核积压 | PENDING 累计 | 不应持续增长 |

## 十二、Definition of Done

八条全过才算完成：

1. 新快照导入后，**你能在 5 分钟内完成当日核实**
2. 未核实的学员，老师端 **100% 不可见**（用接口直接请求验证）
3. 柒柒用**自己的手机**完成 ≥1 条真实跟进记录
4. **第二天她自己又打开了**
5. 三水打不开柒柒的学员
6. 老师点「信息有误」后，该条真的回到核实队列
7. 全站手机号只出现「前 3 后 4」，抓包抓不到全号
8. 一条命令可重新发布

## 十三、数据安全红线

- 后端**永不下发**完整手机号，接口层统一脱敏
- `followup_review_log` 存原值（含全号），**只允许 owner 读，且不提供列表明细接口**
- 日志、异常堆栈里不得出现完整手机号
- 小程序只开体验成员（3 人），不做正式发布，不加公开二维码
- 备份：每日快照 + 跟进记录各导出一份
