# 03 · 命名与目录规范

> 版本 v1.1 · 2026-11-06
> 这份文件回答：**东西该叫什么、放哪里、版本怎么编。** 命名乱了这个仓库两年后没人能维护。

---

## 一、目录

```
hearth/
├── platform/docs/          跨周期约定
├── platform/decisions/     ADR（每个「为什么这么定」）
├── backend/                唯一 Spring Boot 应用
├── miniprogram/            唯一小程序
├── db/migrations/          编号迁移
├── ops/                    发布 / 本地 nginx / 备份
└── cycles/
    ├── _template/          周期模板
    └── cN-<主题>/           每周期一个，只放文档
```

---

## 二、Java 包与类

```
cn.firedance.hearth
├── common         跨模块公共（响应、错误码、脱敏、异常处理）
├── auth           平台级：登录、JWT、Security 配置、账号与角色
└── <module>       业务模块，如 followup
    ├── web        Controller
    ├── service    Service
    ├── mapper     MyBatis Mapper
    ├── domain     DO / DTO / VO
    └── importer   该模块的导入（如有）
```

| 类型 | 命名 | 例子 |
| --- | --- | --- |
| Controller | `<名词>Controller` | `ReviewController` |
| Service | `<名词>Service` | `ReviewService` |
| Mapper | `<名词>Mapper` | `SnapshotMapper` |
| 表实体 | `<名词>DO` | `SnapshotDO` |
| 出参 | `<名词>VO` | `TaskItemVO` |
| 入参 | `<名词>Req` | `FollowupReq` |

**不加 `Impl` 后缀**，**不用 `Util` 做垃圾桶**——`MaskUtil` 这种有明确边界的例外。

## 三、数据库

| 对象 | 规则 | 例子 |
| --- | --- | --- |
| 业务表 | 模块前缀 + 名词 | `followup_snapshot`、`followup_flag` |
| 平台表 | `app_` 前缀 | `app_user`、`app_role`、`app_user_role` |
| 字段 | 小写下划线 | `countcard_lessons` |
| 布尔 | 0/1 的 `TINYINT` 或 `is_` 前缀 | `bought_199` |
| 时间 | `xxx_at`（时间点）/ `xxx_date`（日期） | `reviewed_at` |
| 状态 | `xxx_status` | `review_status` |

**迁移文件**：`VNNN__简短描述.sql`，三位序号从 001 开始，只增不改。

---

## 四、接口路径

```
/api/auth/**            平台级（登录、账号、角色）
/api/health             平台级（探针）
/api/<module>/**        模块级
```

例：`/api/followup/review/groups`、`/api/followup/tasks/today`

资源用复数名词，动词放 HTTP 方法里；确有动作语义的用动词（`batch`、`flag`），但不要滥用。

## 五、版本与 Git

**分支**：`main` 一条。周期内直接提交，不做长期分支（三个人、两周，分支只增加合并成本）。

**版本号**：`v主.次.修`

| 场景 | 规则 | 例 |
| --- | --- | --- |
| 每个周期发布 | 主版本 +1 | C0 = `v0.1.0`、C1 = `v1.0.0`、C2 = `v2.0.0` |
| 周期内修复 | 修版本 +1 | `v1.0.1` |
| 周期内追加小功能 | 次版本 +1 | `v1.1.0` |

`P0` 是工程地基，**不出版本号**——它不是产品。

**Tag**：与版本号同名，`v1.0.0`。

**CHANGELOG**：根目录 `CHANGELOG.md`（Keep a Changelog 格式），每次发布追加一节，由发布脚本自动写入。

**提交信息**：

```
<类型>: <一句话>

类型：feat / fix / docs / refactor / ops / chore
```

一次提交只做一件事，**不要把「顺手改的格式」混进功能提交**。

## 六、周期目录（对齐 Spec-Driven Development）

`cycles/cN-<英文短名>/`，例：`c0-auth`、`c1-followup`

**一个周期目录 = 一个 spec 单元**，按 SDD 三阶段组织：

| 阶段 | 文件 | 回答什么 | 谁读 |
| --- | --- | --- | --- |
| **Requirements** | `spec.md` | 做什么、为什么、做到什么算完 | 人评审 + AI 依据 |
| **Design** | `design.md` | 怎么做：架构、数据模型、关键流程 | 人评审 + AI 依据 |
| **Tasks** | `tasks.md` | 拆成可执行单元：改哪个文件、输入输出、怎么验 | **AI 执行**，人抽查 |

**附件**（属于 Design，按需出现）：

| 文件 | 什么时候有 |
| --- | --- |
| `api.md` | 有新接口时 |
| `wireframe.md` | 有新界面时 |
| `schedule.md` | 排期。**项目管理用，不是执行依据** |

**周期管理文件**：`README.md`（封面）、`review-checklist.md`（评审）、`retro.md`（复盘）。

### 三个常见错误

1. **把 design 写进 spec**：出现「用 MyBatis」「加索引」这类词，就说明越界了
2. **tasks 写到排期粒度**：「D3 做核实接口」不是任务，是日程
3. **为了齐全而建空文件**：没有接口就不建 `api.md`

### tasks.md 的粒度

**一个 task = 一次可独立验证的改动**，通常 0.5–2 小时。每条必须含四项：

| 项 | 例 |
| --- | --- |
| 改哪里 | `followup/service/ReviewService.java` |
| 输入/输出 | 入参 `reasonCode`，出参 `affected` 条数 |
| 怎么验 | `curl -X POST .../batch` 返回 `affected=200` |
| 依赖 | 依赖 T03 完成 |

**判断标准**：如果一个 task 做完后你没法立刻说「成了/没成」，它就是拆得不够细。

## 七、文档命名

`platform/docs/NN-中文名.md`，两位序号，**不加日期**（日期写在文内版本行）。
周期文档用固定小写文件名（`spec.md`），不加序号——目录已经表达了顺序。
